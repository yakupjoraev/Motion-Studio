## Constraints

### README structure

The order matters — it is a funnel from "what is this" to "how do I read the code":

1. **Title, one-line description, badges** (CI, TypeScript strict, Lighthouse, license)
2. **The headline demo GIF** — flow B, 20 seconds, showing composition and export. This is the single
   most important asset in the repository.
3. **What it is** — three sentences, concrete, no marketing
4. **Why it exists** — the gap from `VISION.md`, two paragraphs
5. **Features table** — the one already in the README, verified against what actually shipped
6. **The other three demo GIFs**, each with one line of context
7. **Quick start** — copy-pasteable, and it must actually work from a clean clone
8. **Architecture diagram** + one paragraph, linking to `ARCHITECTURE.md`
9. **Documentation index** — the links, grouped
10. **Tech stack** — the list, with a link to the rationale
11. **Project stats** — real numbers: blocks, presets, effects, tests, coverage, bundle size
12. **Contributing, license**

### The features table must be true

Go through it line by line against the shipped product. Anything that did not ship comes out or gets
qualified. A README claiming a feature that does not work is the fastest way to lose the reader's
trust, and it is the thing they will check.

### `generate-demos.mjs`

```bash
pnpm generate:demos
pnpm generate:demos --flow compose-page
```

Per demo:
1. Playwright drives the flow with realistic pacing — deliberate pauses, visible cursor movement, not
   instant jumps. A demo that moves faster than a human can follow shows nothing.
2. Record WebM at 1440 × 900, 30 fps
3. Convert to GIF: 1200 px wide, palette-optimised, target **under 3 MB** each
4. Keep the WebM alongside (better quality for anyone who wants it)

A **visible cursor** is required — Playwright does not render one, so inject a CSS cursor follower for
the recording. Without it the demo looks like a screen recording of nothing happening.

The recordings must show real interaction: dragging with visible drop indicators, scrubbing with the
value changing, the export dialog with real generated code.

### Why generate rather than record

A hand-recorded GIF is stale the first time the UI changes, and a README with a stale screenshot is
worse than one with none. `pnpm generate:demos` regenerates all four in a few minutes, so it happens on
every release.

Add it to the release checklist in `DEVOPS.md`.

### Quick start must work

Test it literally:

```bash

```

Report any step that failed or needed a command not in the README. This is the most common README
defect and it is entirely preventable.
